If you're learning security, you've probably heard the word reconnaissance thrown around a lot. Recon is the first phase of basically any attack. Before anyone exploits anything, they gather information: what's running, what version it is, who's behind it, and where the weak points are. The problem, when you're learning, is that recon is usually a scattered pile of separate tools and tutorials. SystemAnalyzer chains the whole thing into one project so you can actually watch it happen, step by step.

It's a Python and Flask application. The backend is Flask with a SQLite database, and every read and write goes through a single database module to keep things clean. The frontend is deliberately simple: plain JavaScript, no framework, with a dark, GitHub-style theme. All the heavy work, the scanning and the lookups, runs in background threads, so the interface never freezes while a scan is going. And the dashboard updates itself in real time using server-sent events, so when a background job finishes, the row just updates on its own. No refreshing.

Setup is a single script. It checks the dependencies, makes sure Docker is running for the lab, launches the Flask server, and opens the browser. Every subsystem logs with a short tag, so you can follow exactly what each part is doing as it runs.

Let's talk about where recon actually starts: the tracking pixel. SystemAnalyzer can generate a tracking pixel, which is a tiny, one-by-one-pixel image, along with a small JavaScript payload. In the real world, this is exactly how invisible trackers and malicious lures operate. You embed a tiny image and a script in a page, and the moment someone loads it, it quietly phones home. I'll open the demo page as if I'm an ordinary visitor. I do nothing at all. And watch: a new target appears on the dashboard.

Now let's look at what that page collected, completely passively. The fingerprinting script runs in four stages, and this is the part that surprises people the most.

Stage one happens immediately, the instant the page loads. It generates a canvas fingerprint: the browser is told to draw an invisible image, and that image is hashed. Because of tiny differences in how each machine renders graphics, that hash is nearly unique to your device. The same idea is used for a WebGL hash from your graphics stack, and an audio hash from your sound stack. Then it collects the easy stuff: screen resolution, color depth, timezone, platform, the number of CPU cores, how much memory you have, touch support, your installed fonts, and your browser plugins. It can even tell whether you're using dark mode.

Stage two runs asynchronously, just after load. Now the script asks your browser some questions. How many cameras, microphones, and speakers do you have? Just the counts; it can't see or hear through them. What's the permission state for things like geolocation and notifications? And which text-to-speech voices are installed on your system? That last one sounds harmless, but your installed voice list is shockingly identifying.

Stage three is app probing, and this one is clever and a little unsettling. The script tries to detect desktop applications you have running by quietly probing the local network ports that popular apps listen on, the ports used by Discord, Spotify, Steam, Visual Studio Code, Zoom, and others. If one of those ports answers, it's a very good guess that you have that app open right now.

Stage four is GPS, and only if precise geolocation is explicitly enabled. That one requires a visible permission prompt, so the browser does protect you there. But put all four stages together, and you have a profile that can identify this exact browser across sessions, with no cookies involved at all. The defensive takeaway is important: this is precisely why anti-fingerprinting browsers randomize your canvas and WebGL signatures, and it's why private browsing mode alone does not hide you. Private mode clears cookies; it does nothing about your fonts, your graphics card, or your running apps.

That's everything the client leaked. Now let's see what the server does with the connection it just received.

The moment that pixel was hit, the server didn't just log the visit. It kicked off a background nmap scan against the source host. Nmap is the classic port scanner, and here are its results coming in: the open ports, the service running on each one, and a best guess at the operating system. If you're new to this, think of an open port as a door, and the service behind it, say OpenSSH, or an old Apache, tells an attacker exactly what's listening and which version it is. Notice that the tool grabs version banners wherever it can. Hold on to that detail, because version numbers are the hinge that everything else swings on.

While nmap was running, a second background worker looked up the IP address itself. This pulls geolocation down to the city level, the internet service provider or hosting company, and, importantly, whether the address looks like a VPN, a proxy, or a hosting data center. That last signal is the interesting one defensively. If what looks like an ordinary home user is actually coming from a data center proxy, that's a mismatch worth noticing. Analysts use exactly this kind of enrichment to separate normal traffic from something that's trying to hide its origin.

Now the payoff. Remember those service versions? SystemAnalyzer takes them, plus the browser and operating system it fingerprinted, and queries the National Vulnerability Database, the official government feed of known security flaws. It pulls back the vulnerabilities that match, each with its CVSS score, which is the standard severity rating from zero to ten. And this is exactly why version numbers matter so much. A plain note that port twenty-two is open is boring. But port twenty-two running a specific version with three known high-severity vulnerabilities, that is a finding. The tool color-codes everything: red for critical, amber for medium, and rolls it all up into a single risk score for each target. Back on the dashboard, every target carries that score, so you can instantly sort and see which host is the most exposed. Or, if you're the one defending, which of your own machines needs patching first.

So in one screen, we've gone from a visitor doing absolutely nothing to a prioritized, scored vulnerability list. Now let's make it explain itself.

Raw lists of vulnerabilities are useful, but when you're learning, what you really want to know is: so what? That's the job of the AI security advisor. I click analyze, and it takes the full picture, the fingerprint, the open ports, and the matched vulnerabilities, and writes a human-readable assessment that streams in live. Here's a design choice I really like. It tries a local model first. It's wired for a local model running on my own machine, so by default nothing leaves my laptop, which, for a security tool, is exactly what you want. If the local model isn't available, it falls back to a cloud provider. Local first, cloud as backup.

It doesn't stop at a summary. It will suggest attack paths, a plausible chain of how those separate findings connect into an actual compromise, and it builds a threat-actor-style profile of the target. For a student, this is the gold, because it's not just what is vulnerable, it's the reasoning that an experienced analyst would walk through. And my favorite touch is the natural-language query box. I type a plain-English question, the model turns it into a database query, runs it safely, and hands me back the answer. It's a small, contained example of the text-to-query pattern you're going to see everywhere now.

Now for the last piece, and honestly the most fun if you're learning: there's a complete capture-the-flag lab built right in. Each of these cards is a deliberately vulnerable machine running inside its own Docker container. The idea of capture-the-flag is simple. There's a hidden flag, a secret string, somewhere on the box, and your job is to exploit the machine to find it. I pick a challenge and press start. Behind the scenes, the app talks to Docker, spins up the container for that box, and because it's wired into the same engine, it will even run nmap against it to give you a starting point. When you solve the challenge, you submit the flag, it gets verified by its hash, and your score updates on the leaderboard. So a single application is both the recon tool and a safe, legal playground to practice the actual exploitation, on machines that exist only to be broken. That is how you learn offensive security without ever touching something you shouldn't.
